# 课程题库语义答疑

把 496 道自然辩证法题库做成一个能用**大白话提问**的检索系统，并配套一套可复现的评测。

核心问题不是"能不能检索到"，而是**"学生用口语问，系统还能不能找对"**。

---

## 结果

150 条测试用例（50 道题 × 2–3 种学生口语问法），指标为 hit@1（第一位就是正确题目）：

| 方案 | hit@1 | hit@3 |
|---|---|---|
| 纯向量检索（基线） | 46.7% | 74.0% |
| 口语 → 书面改写 | 43.3% | 70.7% |
| 关键词/术语扩展 | 24.0% | 56.0% |
| 纯 BM25 | 53.3% | 72.7% |
| 向量 0.5 + BM25 0.5 | 58.0% | 79.3% |
| **+ 解析入索引（最终）** | **58.7%** | **82.0%** |

随机基线 hit@1 = 0.20%。

**最终：hit@1 从 46.7% 提升到 58.7%（相对 +26%），hit@3 从 74.0% 提升到 82.0%。**

上表是**检索命中率**（正确答案有没有排进前 k），不等于"答对了"。
另抽 10 条跑完整流程做了生成质量检查：**回答正确 10/10，硬答 0 条**，题库外的问题能正确拒答。

再往上做了一层 Agent（多步工具调用），另建 17 条评测：**17/17，连跑两轮一致**，平均每条 1.4 次工具调用、4.6 秒。
详见下方「从检索到 Agent」。

最后把它部署成 HTTP 服务并压测：**单核约 8 QPS，40 并发内 p95 ≈ 4.3 秒，单次请求约 0.11 分钱**。
详见「服务化」。

## 三个发现

**1. 让查询"更像文档"是无效的，甚至有害。**

用大模型把"四大发明是哪四个来着"改写成"中国古代四大发明的具体内容是什么"，hit@1 反而降了 3.3 个点。
原因是改写只做了语气正式化（啥→什么），而检索的鸿沟在词汇对齐（最牛→高峰）。
更进一步，把问题扩展成 12 个同义术语后，hit@1 暴跌到 24.0%——
**向量是加权平均，堆泛化词会把查询拉向整门课的"质心"，离具体那道题更远。**

**2. 纯 BM25 的 top-1 精度高于向量检索（53.3% vs 46.7%），但召回广度更低（hit@3 72.7% vs 74.0%）。**

两者错在不同的地方：BM25 认词，向量认意思。所以融合有效——**互补的前提是"错得不一样"**。

**3. 按"题目 ID"打分是坏指标。**

题库里有大量"考同一知识点但表述不同"的题（判断题改写选择题、同一句挖不同的空）。
按 ID 打分会把这类"答对了"判成"答错了"，严格口径与等价口径相差 21 个点。
**这也是为什么评测集不能拿被测系统的输出反推**——等价标注一旦参考了基线结果，就会反过来偏袒基线。

## 运行

环境：Python 3.11 + PyTorch（CPU 即可），无需显卡。

```bash
# 1. 解析题库
python scripts/parse_questions.py

# 2. 建索引（首次会下载 embedding 模型，约 100MB）
python scripts/build_index.py

# 3. 跑一遍基线
python scripts/run_eval.py

# 4. 随便问
python scripts/ask.py

# 5. Agent 对话（模型自己决定查什么）
python scripts/agent.py

# 6. Agent 评测
python scripts/eval_agent.py

# 7. 起服务（浏览器打开 http://127.0.0.1:8000/docs）
python -m uvicorn server:app --port 8000

# 8. 压测（服务需先跑起来）
python scripts/loadtest.py -c 20 -r 1
```

依赖：`torch` `transformers==4.46.3` `jieba` `numpy` `openpyxl` `scikit-learn`

> 国内注意：`transformers` 需锁 `4.46.3`（5.x 要求 torch≥2.6）；HF 官网不通，代码里已设 `HF_ENDPOINT=https://hf-mirror.com`。
> Windows 上若报 OpenMP 冲突，设环境变量 `KMP_DUPLICATE_LIB_OK=TRUE`。

## 局限

- 测试集由大模型起草后人工校订，**比真实学生提问更"懂事"**，因此基线可能偏乐观
- 等价组只标注了基线 top-3 范围内的候选，覆盖不全
- 未做 Rerank 精排（CPU 上较慢），这是最对症的下一步
- 只验证了单一课程语料，规模 496 题，不能代表更大题库的表现
- Agent 评测 17 条已全部通过，**不再有区分度**；且语义类答案靠词表判分判不干净（详见下文）

## 加生成之后（`ask.py`）

默认流程：混合检索 top-3 → 把题目、答案、**解析**交给大模型 → 口语回答，**答不出就拒答**。
加 `--no-gen` 只做检索，用来单独观察检索环节。

**为什么要加拒答**：检索永远会返回 top-3，哪怕库里根本没有相关内容。直接把错题喂给模型，它会照着编出一段通顺但完全错误的回答——这比答不出来危险得多。

**为什么不用相似度阈值做拒答**：实测过（`probe_threshold.py`），不行。

| 查询类型 | top-1 向量相似度 |
|---|---|
| 检索命中的 | 0.527 ~ 0.787 |
| 检索**没**命中的 | 0.505 ~ 0.788 |
| 完全无关（红烧肉、天气） | 0.458 ~ 0.533 |

命中和没命中的分布**完全重叠**——相似度高不代表检索对了。所以改用让模型判断相关性，实测有效：

- 「那个系统有啥特点」→ 正确答出"开放性、动态性、整体性、层次性"
- 「红烧肉怎么做才好吃」→ 输出"题库里没有找到"

**暴露出的真问题（已解决）**：旧的题库只有"答案是什么"，171 道判断题的答案是两个字——正确/错误，知识藏在题干里。
「自然辩证法都研究哪些内容」检索到了三道正相关的判断题，模型仍拒答，因为三道的答案都是"错误"（各自漏掉一项），语料里从未给出完整答案。**模型拒绝猜，这是对的。**

换成带解析的题库后（`questions_v2.json`，496 题、1.7 万字解析），同一个问题回答正确：

> 自然辩证法主要研究自然观、科技观（史）、科学认识方法论、科技与社会这几块内容。注意别漏掉"自然观"或"科学认识方法论"，少了就不完整。

> 这条比任何技巧都重要：**RAG 的效果上限由语料决定，不由模型决定。** 检索侧换模型、调参数，都不如补一份带解析的语料管用。

## 从检索到 Agent（`agent.py`）

检索回答的是"哪几条最像这句话"。「哪几讲提到盖伦」「一共几道提到第谷」「判断题里有几道答案是错的」这些问题问的是**覆盖和计数**，相似度再高也算不出来——`ask.py` 遇到它们只能拒答。

所以加了一层 Agent：模型每一步自己决定调哪个工具，看到结果再决定下一步，够了才回答。

| 工具 | 作用 |
|---|---|
| `search` | 向量 + BM25 混合检索 top-k，用于"不确定有没有相关内容" |
| `detail` | 按题号取完整题干、选项、答案、解析 |
| `stats` | 按讲次 / 题型 / 答案统计，返回数量与分布 |
| `grep` | 全库逐题扫关键词，返回总数、讲次分布、每道题明细 |

**三个终止条件**，缺一不可：模型输出 `final` / 步数上限 8 / 同一工具加同样参数重复调用（检测原地打转）。

第三个是最容易被忽略的。做 AI 编程助手实验时见过模型反复生成同样文件停不下来，根因就是没有收敛判断——步数上限只能兜底，重复检测才是真正的闸门。

不用 LangChain 的理由：这个循环不到 60 行，写成自己的，才能回答"终止条件怎么定""模型打转怎么办"。套框架的人答不上来。

### 评测：17 条，17/17

单独一套，和检索那 150 条不通用（那些测的是"有没有命中那道题"）。分五类：覆盖 4、统计 6、问细节 4、集合运算 2、拒答 1。

平均 **1.4 次工具调用、4.6 秒/条**。这个数比改之前低——加了工具、加了步数，调用次数反而下降，因为工具对了就不需要反复试错。

### 三条失败，三种修法

**① 覆盖类答错：「哪几讲提到盖伦」答"只有第二讲"，真值是两讲共 3 道。**

它自己的检索结果里就摆着第四讲那两道，没看见。根因是 `search` 返回 top-k，模型把这 5 条当成了全集。→ 加 `grep`，返回 total 和全部命中。

**② 数不出来：「判断题里有几道答案是错的」拒答"工具没法按答案筛选"。**

加了 `answer` 维度后一次调用得出 87 道。改之前它用 `detail` 逐题读，8 步只核对了 5 道就耗尽预算，交了一份"给不出准确总数"的半成品。

**③ 数字差 1：判断题答案=错误，按字符串筛是 86，实际是 87。**

题库有 1 道（`judge-第四讲-8`）的答案写成"否"而不是"错误"。这种错最麻烦——不报错，只是少 1 道。→ 归一化（否/错/×/F → 错误）。

### 判分器自己也要被验证

这轮最值钱的教训不是系统哪里错了，是**评测本身错了两次**：

- 第一版跑出 10/10，其实第 9 条是假的：标准答案被我写成"哥白尼"（实为地心说），而判分只做了 `in` 判断，把"未接受哥白尼"判成命中。标准答案错 + 断言太宽，两者合谋给出了漂亮的假分数。
- 「盖伦和牛顿是否同讲」试了三种判法：禁止提其他讲次（误杀）、要求出现"唯一/重合"（换个说法就误杀）、最后只查有没有说"第四讲"（松了，但不再误杀）。

现在 `eval_agent.py` 里有两道前置校验，任何一道不过就直接退出：

1. `selftest()`：19 个已知对错的样本先验证判分逻辑
2. `raw_scan()`：标准答案写死在脚本里，启动时用独立扫描核对一遍，防"代码改了、标准答案跟着漂"

> **评测集的作用不是给出一个好看的数字，是持续找出下一个洞。** 每补一个洞分数就回到 100%，然后再加更难的题。17/17 现在不再有区分度——这句话本身就该写进来。

## 服务化：从"我电脑上能跑"到"别人能调"

前面所有指标都是"我一个人、在我机器上"测的：hit@1 58.7%、Agent 17/17。

但**"效果"和"能力"是两件事**。一个人用 1.7 秒觉得挺好，一百个人同时问就未必。所以加了一层服务：

```
POST /ask   {"q": "第三讲有多少道判断题"}
         →  {"answer": "...", "tools": ["stats"], "elapsed_ms": 1654,
             "tokens": 1174, "prompt_tokens": 1676, "completion_tokens": 97,
             "cache_hit_tokens": 1280}
```

`GET /health` 检查索引是否加载好；`run_server.bat` 双击启动，浏览器打开 `/docs` 可以直接点着发请求。

### 五个数字

| 项 | 实测值 | 怎么来的 |
|---|---|---|
| 承载 | **约 8 QPS**，40 并发内 p95 ≈ 4.3 秒 | `loadtest.py` 压 20/50/100 并发 |
| 单次成本 | **约 0.11 分钱**（1000 次约 1.1 元，1 万次约 11 元） | 17 条题逐条量的平均 |
| 输入构成 | 平均 1961 输入 + 118 输出，其中 **73% 输入命中缓存** | `usage.prompt_cache_hit_tokens` |
| 降级 | 模型 15 秒超时 → 退回检索 top-3 | 故意把超时设成 1ms 验证 |
| 限流 | 40 并发，超出返回 429 | 中间件计数 |

成本跟"调几次模型"强相关：1 次工具调用（2 次模型调用）约 0.07~0.10 分，3 次工具调用涨到 0.21 分。**平均每条题 1.4 次工具调用。**

### 压测：延迟会随负载恶化，除非加限流

| 场景 | 通过 | 拒绝 | p50 | p95 | 最慢 | 吞吐 |
|---|---|---|---|---|---|---|
| 无限流 · 20 并发 | 20 | 0 | 2.99s | 4.58s | 4.75s | 4.2 /s |
| 无限流 · 50 并发 | 50 | 0 | 3.30s | 5.78s | 6.66s | 7.48 /s |
| 无限流 · 100 并发 | 100 | 0 | 6.67s | **8.96s** | **15.00s** | 6.66 /s |
| 限流 40 · 50 并发 | 40 | 10 | 3.21s | **4.25s** | 4.85s | 8.21 /s |
| 限流 40 · 100 并发 | 47 | 53 | 3.49s | 4.99s | 5.83s | 8.04 /s |

**看 p95 那一列**：不限流时随负载 4.58 → 5.78 → 8.96 一路恶化；限流后压在 4.25~4.99，不再随负载涨。

**限流不是提速，是给延迟封顶。** 它的取舍是：拒掉一部分请求，换取被服务的那部分保持可预测。100 并发下拒掉一半，但通过的那些 p95 从 8.96 降到 4.99。

### 三个只有压过/算过才会发现的坑

**① 限流写在处理函数里是无效的**

第一版写在 `ask()` 开头，100 并发时一个 429 都没出现。因为 FastAPI 的线程池只有 40 条线程，另外 60 个请求在"门外排队"，根本没执行到那行判断。

> 函数内的限流只能挡"已经在跑"的请求，挡不住"在等"的请求。必须放在中间件（事件循环层），请求一进来就计数。

**② 一次请求其实调了两次模型**

不是一次。第一次是"决定用哪个工具"，第二次是"把工具结果组织成人话"。原先只记最后一次的 usage，**成本被低估一半**。修法是把逐步用量累加。

**③ 78% 的输入命中缓存，因为系统提示是固定的**

缓存命中的输入便宜 50 倍（$0.003 vs $0.15 / 百万 token）。这条不记，成本会被高估两倍半。

**推论**：成本几乎全在输入——输入 1725、输出 107，输出只占 6% 的量。想省钱不是让回答变短，而是**压缩上下文**：精简系统提示、控制 `grep` 返回条数（默认 15 条明细，一次几百 token）。

### 一次成本优化：把系统提示精简掉 23%

先量再改。逐次记录每次模型调用的 token 构成：

| 问题 | 第 1 次调用 | 第 2 次调用 | 工具返回占比 |
|---|---|---|---|
| 第三讲多少判断题 | 746 | 930（工具返回 264 字符） | 10% |
| 哪几讲提到盖伦 | 747 | 1039（工具返回 501 字符） | 15% |

**每次调用固定带约 730 个 token 的系统提示**（工具清单 + 规则），两次就是 1460——占输入的 85%。工具返回只占一成多。

所以砍 `grep` 条数是省不出钱的，得改那个"每次都要带"的东西。

把 9 条规则里重复的表述合并（"用 stats 不要用 search 猜"和"问数量用 stats"其实是一句），1320 字符压到 1019：

- 单次输入：1676 → **1318（−21%）**
- 17 条评测：**仍是 17/17**

**教训：省成本要动"每次调用都付的钱"，不是"偶尔很大的一笔"。**

### 一个实现细节

`/ask` 写成 `def` 而不是 `async def`：`agent.run()` 内部调模型、跑 embedding 全是同步阻塞，写成 `async` 会卡住 uvicorn 唯一的事件循环线程——第一个请求没回来，后面所有人排队，表现得像"服务死了"。写成 `def`，FastAPI 会把它放进线程池。

## 错题本：把"答完就忘"变成"记得你错在哪"

服务原本是无记忆的：答完就忘，学生复习时问"我上次错在哪"，它答不出。

错题本解决的正是这件事，也顺带解释了为什么它的数据格式长这样。

### 三个端点

| 端点 | 作用 |
|---|---|
| `POST /wrong` | 上报一条错题。**只需 qid**，讲次与正确答案从题库补全 |
| `GET /wrong?lecture=第五讲&limit=20` | 按讲次查，最近的在前 |
| `GET /wrong/stats` | 总条数 / 按讲次 / 去重（同一题错多次算一道） |

实测（只传题号，讲次和答案自动补齐）：

```json
POST /wrong  {"qid":"single-第五讲-1","question":"第谷用啥观测","wrong":"望远镜"}
→ {"ok":true,"record":{"t":"2026-11-16 15:52:33","qid":"single-第五讲-1",
    "lecture":"第五讲","q":"第谷用啥观测","wrong":"望远镜","right":"肉眼"}}
```

### 四个设计决定

**① 用 jsonl 而不是 json 数组**
追加记录不用读全文重写。数组要整份覆盖，记录一多、并发一高就容易丢数据。

**② 上报只要题号**
讲次和正确答案在题库里是现成的，让前端再传一遍，只会多一个传错的机会。**单一事实来源。**

**③ 记录不去重，去重是统计口径**
学生错三次就记三条——保留的是"错了三次"这个事实。去重只在 `stats()` 里做。

**④ 读的时候跳过坏行**
`json.loads` 包了 `try/except`：一条坏记录不该让整个查询挂掉。这是降级，不是根治。

### 一个诚实记录：病因没被证实

写这个功能时，想起前面 `server.py` 的日志出现过坏行（362 行坏 3 行），于是加了写锁。

但做对照实验——把锁换成 `nullcontext`、200 个线程并发写入——**坏行 0，没复现。**

| 已知 | 未知 |
|---|---|
| 坏数据形态是"开头被覆盖、只剩后半截"，符合两条写入算出同一 EOF 互相盖 | 为什么这次复现不出来 |

所以能说的是"**锁是对的**"，不能说"**我证明了不加锁会坏**"。

偶发 bug 的常态就是这样：**修复能验证，病因不能稳定复现。** 这也是为什么修之前要先想办法稳定复现——否则你只是换了个写法，不知道问题还在不在。

## 教材 RAG：从一本扫描 PDF 到带引用的答案

上面那些都是在「496 条结构化题库」上做的。这批数据太干净——每条自带题号、答案、
解析，切多大、切在哪都不是问题。而真实场景拿到的是**一本扫描版教材**。

于是另起一条链路：教材 PDF → OCR → 清洗 → 切片 → 向量检索 → 重排 → 生成。
两条链路不共享流程，只共享 embedding 模型和评测方法。

### 一、数据：230 页扫描件

PDF 没有文字层（230 页全是图片，所谓"文字"只有 73 个字，还是坏的 OCR 残留）。
所以走 OCR：`pypdfium2` 渲染 2 倍 + `rapidocr` 识别，**每页 2.7 秒，230 页 9.9 分钟**。

清洗有两条经验：

| 问题 | 做法 |
|---|---|
| 页眉每章都不同（"第X章 XXX"） | **不能硬编码**，改用统计：同一短行在 8 页以上原样重复 → 判为页眉。识别 12 条，去掉 470 行 |
| 脚注被 OCR 并进句子中间 | 如「都包含经验技①习近平：《…》第34版，第34页。能，都使用机器」。占 9% 的字，纯噪声，正则清掉 284 处 |

**结果：113,509 字 → 102,285 字。**

OCR 和清洗刻意分成两个脚本：清洗规则改了好几轮，写在一起的话每改一次要重跑 10 分钟。

### 二、切片：参数是量出来的

**为什么必须切**：`bge-small` 只吃 512 token（约 300~400 汉字），整篇 7000 字丢进去，
只看得到前 400 字；而且一篇一向量等于把 9 个主题平均成一个点——和前面
「扩词导致 hit@1 掉 22.7」是同一个病。

**指标改了三版才公平**：

| 版本 | 量的东西 | 为什么错 |
|---|---|---|
| v1 | 被块边界"切断"的题数 | 算出 614 道，而题库只有 496 道——重叠区重复计数了 |
| v2 | 至少被边界碰到过的题 | 重叠反而让数字变大（205 → 449），说明量的不是信息丢失 |
| v3 | **没有任何一块完整包含的段落数** | 这才是"检索到了也读不全" |

**评测集怎么来的**（没有标注是最大的难题）：用教材原文的**小节标题**当查询，
答案位置由标题位置客观决定。144 条，覆盖正文 81%。不模型生成问题——
那会抄原文措辞，让检索显得虚高。

**结果（144 条）**：

| 切片 | 块数 | 均长 | 命中@1 | 命中@3 | 命中@5 | 喂入字数@5 |
|---|---|---|---|---|---|---|
| 200/0 | 512 | 200 | 26% | 41% | 44% | 1000 |
| 300/100 | 511 | 300 | 31% | 56% | 65% | 1500 |
| **500/100** | 256 | 499 | **38%** | **62%** | **75%** | 2495 |
| 800/100 | 146 | 800 | 31% | 57% | 65% | 4000 |
| 1200/100 | 93 | 1199 | 28% | 48% | 62% | 5995 |

两个结论：

1. **重叠有效**：同为 300 字，@5 从 52% 到 65%
2. **块长有最优区间**，两头都掉。最优 500 字 ≈ 评测集的**小节长度中位数 480 字**
   —— 块长应该匹配一个知识点的自然长度，不是"越小越准"

**按句子边界切（一条诚实的负面结果）**：
纯按字数切时，只有 **4%** 的块以句末标点结尾——96% 切在句子中间。
改成切到目标位置附近往后找句号后，100% 落在句号后（块长 371~617）。

局部确实修好了一条：「辩证唯物主义自然观的定义」原来被切成两半，两块都不像定义，
重排给 5.12/5.15，而一段通顺的无关段落拿了 7.01。改完引用命中正确小节，答案完整。

但**全局指标没变**（重排后 @1 73%→72%，@5 86%→83%，都在 ±7 噪声内）。
所以只能说"修掉了一个具体缺陷"，不能说"断句提升了效果"。

### 三、向量库：换库不等于换算法

| 场景 | 结果 |
|---|---|
| 167 块 | numpy 0.021ms vs FAISS 扁平 0.018ms —— **没有收益** |
| 10 万条 | 扁平 12.56ms（和暴力同算法，只快常数）；HNSW ef=80 **0.24ms 且召回 100%** |
| 同召回比速度 | HNSW ef=80 (0.24ms) vs IVF nprobe=8 (1.91ms)，**快 8 倍** |

`IVF` 随 nprobe 线性增长（每多查一个桶 = 多算固定条数），`HNSW` 是次线性（图中多走几步）。
**报"快了多少倍"必须配召回率，否则等于说"我少查了所以快了"。**

造合成数据时连错两版：iid 随机向量（高维近似正交、无聚类，ANN 全失效）、
真实向量+扰动复制（大量近似重复，top-k 全是平局）。第三版用"聚类中心+归一化噪声"才成立。

### 四、重排：命中@1 翻倍，代价 2 秒

粗排取 10 条（这个 10 是算出来的：池子 5 的天花板 75%、10 是 87%、20 是 94%，
但耗时分别 0.8 / 1.5 / 3.0 秒），再交给 `bge-reranker-base` 逐条打分重排。

| 指标 | 重排前 | 重排后 |
|---|---|---|
| 命中@1 | 38% | **73%**（+35pt） |
| 命中@3 | 62% | 86% |
| 命中@5 | 75% | 86% |

**名次提前 66 条，退后 3 条。** 有 5 条从第 10 位直接被提到第 1。

代价：**每候选 205ms，10 条 2.1 秒**，全链路 2.9~3.0 秒。
（重排首包要 5.6 秒，服务启动时必须预热，否则第一个用户等 7 秒。）

**为什么重排能修好向量检索修不好的**：向量检索把 query 和文档各自压成一个向量再比，
两节都含"朴素唯物主义"时几乎是同一个点；重排把两段拼起来喂进模型，能看见"观点"和"特征"的差别。

### 五、生成：抽查 10 条

10 条覆盖四类：单点概念 3、需综合 3、容易混 2、**教材里没有 2**（"第谷用什么观测"、"红烧肉怎么做"）。
判断标准是「**能不能在引用的原文里找到依据**」，不是「我觉得对不对」。

结果：**9 条有据，1 条 ❌**。

那条 ❌ 值得记：模型说「教材里没有直接讲到」，而教材第 36 页有完整定义。
病因两层——切片把定义句切断导致重排给低分，而模型只看到 3 个片段，
却断言了"整本书没有"。

**这个错误比编造更隐蔽**：编造你能看出来，而它让你真的以为书上没有，然后放弃查书。
正确说法应该是「我检索到的片段里没有」。

两条陷阱题都正确拒答（重排分数 −4.4、−6.4），没有硬编。

### 六、边界

- 引用标签用「起止节 → 起止节」，因为 500 字的块常跨节，只标起点会说错
- 块跨节的根因是按字符切；按小节边界切可能更好，但小节长 250~2500 字，块长会很不均，未验证
- 没有做阈值拒答：负例只有 2 条，定不出可靠阈值；而且生成只占 0.5~1.1 秒，省它意义不大
